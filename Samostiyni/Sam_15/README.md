## Опис проєкту

Консольний проєкт `IndependentWork14` демонструє політику повторних спроб для будь-якої операції `Func<T>`.

## Реалізація

У прикладі дозволено 3 повтори після початкового виклику. Початкова затримка становить 100 мс, а jitter — ±20%. Індекс першого повтору дорівнює нулю. Перший виклик повертає залишок після двох збоїв, другий передає виняток після чотирьох спроб. `shouldRetry` у першому виклику дозволяє повторювати `IOException`.

## Висновок і контрольні запитання

1. Експоненційна затримка дає залежності більше часу на відновлення після кожної невдачі. Фіксований короткий інтервал продовжує створювати навантаження протягом усього збою.
2. Jitter випадково зміщує затримки клієнтів, щоб вони рідше виконували повтори одночасно. Для базових 100, 200 та 400 мс затримки в прикладі лежать у межах 80–120, 160–240 та 320–480 мс.
3. `shouldRetry` дозволяє повторювати лише обрані винятки. Якщо предикат повертає `false`, поточний виняток передається викликачеві одразу.
4. Повтор доречний для тимчасових збоїв та ідемпотентних операцій. Помилки валідації, відсутність прав і скасування слід відхиляти без повтору. Якщо платіж, запис або надсилання повідомлення вже могли відбутися, потрібна ідемпотентність або усунення дублікатів за ключем.

Синхронна реалізація блокує потік на час очікування. Для сервісних викликів зазвичай потрібні асинхронне очікування, скасування та загальна межа часу.
